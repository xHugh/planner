# Design

## Context

四条缺陷各自独立，但都来自同一类问题：把「数据里可能出现的坏形态」当成了不会出现。

**编辑态判定**：`openWorkout()`（`js/log.js:439-517`）把 `editingId = s.id` 存进 `state.wo`，之后三处判定「现在是不是编辑态」全部依赖 `wo.editingId` 的真值——`log.js:324`（离开提示）、`log.js:679-680`（按钮文案）、`log.js:721`（保存时覆盖还是新建）。而 `validSessions()`（`core.js:197-202`）并不要求记录有 `id`，所以一条没有 `id` 的记录会正常出现在历史列表里，点编辑后 `editingId` 是 `undefined` → 走成「完成训练」→ `db.sessions.push()` 生成一条重复记录。

**计时字段**：`validDraft()`（`core.js:207-213`）只校验结构，不看 `elapsedMs` / `lastResumedAt`；`validateDB()`（`progress.js:340-386`）同样不校验草稿的计时字段。于是字符串值可以从手改 localStorage 或导入的备份进来：`pauseClock()`（`log.js:349-352`）算出 `NaN`，`openWorkout()` 的间隔并入（`log.js:504-508`）把 `NaN` 灌进 `elapsedMs`，`finishWorkout()`（`log.js:746-749`）得到 `duration = NaN` → `Math.max(NaN, 1)` 仍是 `NaN` → `JSON.stringify` 写成 `null`，训练页上则显示 `NaN:NaN`。

**草稿归一化**：`normalizeDrafts()`（`core.js:221-234`）逐个键处理并写 `out[nk] = dr`，同一 `dayId+date` 同时存在规范键与非规范键时，谁在后面谁覆盖谁，取决于键的插入顺序。

**跨标签页合并**：`app.js:63` 的 `db.sessions.map(s => s.id)` 遍历的是原始 `db.sessions`，遇到 `null` 记录直接抛 `TypeError`，整段合并静默中止。

## Goals / Non-Goals

**Goals:**
- 坏形态的数据不再改变用户可观察到的行为（不重复记录、不出现 `NaN`、不丢草稿、不抛未捕获异常）。
- 判定的依据从「数据里恰好有的字段」改成「这次操作到底是什么」。

**Non-Goals:**
- 不引入数据迁移、不给旧记录补写 `id`、不改变存储结构。
- 不把「带非法计时字段的草稿」判为坏草稿清掉——那是丢用户数据，比显示 `NaN` 更糟。

## Decisions

### 决策 1：编辑态用显式布尔量，不再从 `editingId` 的真值推断

`state.wo` 增加 `isEdit`（进入编辑分支即为真），`editingId` 退化为「这条记录的 id」这一项数据，可以是 `undefined`。三处判定点统一改用 `isEdit`。

- 备选：给缺 `id` 的记录在加载时补一个 `uid()`。否决——改动了用户数据的内容与导出结果，也把「重复 id 防误伤」的定位策略搅浑；而且用户从未要求这条记录有 id，补一个 id 反而制造了一个看起来合法、实际是伪造的标识。

### 决策 2：计时字段在加载路径归一，而不是在 `validDraft()` 里判坏

`validDraft()` 的职责是「这份草稿的结构能不能用」，用于过滤与清理；计时字段非法不影响结构可用性——草稿里可能已经有用户勾好的组。把它判为坏草稿会直接丢掉这些组。因此归一放在加载路径（`openWorkout()`）：已累计时长无法转成数字时按 0 起算（能转成数字的字符串按数值使用，不丢用户已累计的时间），计时起点不是有效数字时按「未在计时」处理，间隔并入前先确认起点是有限数字。

- 备选 A：在 `validDraft()` 里加计时字段校验。否决——会连带清掉带非数字计时字段的草稿，丢用户数据，与「坏数据不得让页面崩溃但也不得丢内容」的既有立场冲突。
- 备选 B：只在写盘时归一。否决——训练页在归一之前就已经显示 `NaN:NaN`，用户先看到坏数据。

### 决策 3：导入端拒绝、加载端容错，两层同时保留

`validateDB()` 增加草稿计时字段校验（与 `rir` / `maxPain` / `durationMin` 同一口径），挡住明显坏数据；加载端（决策 2）兜住手改 localStorage 与更早的备份。两层职责不同，不冲突。

### 决策 4：草稿归一化时规范键优先

`out[nk]` 只在尚未被占用时写入；同一 `dayId+date` 同时存在规范键与非规范键时，保留规范键下的那份。理由是规范键是草稿的唯一身份，身份冲突时应当保住「已经是规范身份」的那份，而不是让键的插入顺序决定。

### 决策 5：跨标签页合并跳过 `null` 记录

`db.sessions.map(s => s.id)` 改为跳过 `null`（`validSessions()` 已经在过滤层做这件事，这里遍历的是原始容器）。

## Risks / Trade-offs

- **非法计时字段降级为 0，用户可能以为训练时长丢了** → 缓解：这类数据本来就不可解释，`NaN` 与 `null` 只会更糟；降级后界面显示 `00:00`、记录时长为 1 分钟，是可解释的结果。
- **无 id 的记录导出后无法再次导入**（`validateDB()` 要求记录有 `id`）→ 既有行为，本次不改；记在 Risks 里，后续可考虑导入时为缺 `id` 的记录补 id。
- **`pageshow` 恢复时的计时**：`pagehide` 已经会暂停并落盘，但页面从往返缓存恢复时没有 `visibilitychange`，计时会停在恢复前的读数 → 补 `pageshow` 处理：`event.persisted` 为真且训练未结束时恢复计时；本应用没有出站导航，往返缓存场景少见，因此按稳健性补丁处理，不作为主要缺陷。
- **`isEdit` 改动散在三处判定点，漏改会导致按钮文案与实际行为不一致** → 缓解：新增用例同时断言按钮文案与保存结果。
- **草稿归一化改成规范键优先后，非规范键那份草稿的内容会被丢弃** → 这是身份冲突时必须做的取舍：保留两份会让「继续」打开哪一份变得不确定。
