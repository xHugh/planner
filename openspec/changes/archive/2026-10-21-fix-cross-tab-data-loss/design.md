# Design

## Context

跨标签页同步只有一处入口：`app.js` 的 `storage` 监听（`app.js:57-74`），它按本标签页是否在训练中分成两条路径。

- 训练中（`state.wo` 非空）：按 `id` 把对方新增的 `sessions` 并入内存，**不动 `db.drafts`**，提示一次后 return。
- 空闲：整量替换 `db.sessions` 与 `db.drafts`，归一化草稿键后重绘当前页。

写盘是整量的：`saveDB()`（`core.js:183-191`）把整个 `db`（含 `sessions` 与 `drafts`）`JSON.stringify` 后写进 `gym4.db.v1`。因此内存里的 `db.drafts` 只要是陈旧的，下一次落盘就会把磁盘上别人新增的草稿覆盖掉。

记录定位则是「以对象引用为准」：`showSessionSheet()` 捕获记录对象，`log.js:303` 删除与 `log.js:725` 编辑保存都用 `db.sessions.indexOf(对象)` 定位。空闲分支整量替换 `db.sessions` 后这些对象引用全部失效。

两个约束互相拉扯：AGENTS.md 要求「不要用 `id` 匹配——手改 localStorage 可能出现重复 `id`」，而跨标签页同步又会让引用失效。

## Goals / Non-Goals

**Goals:**
- 训练中的标签页落盘不再抹掉别的标签页尚未完成的训练。
- 跨标签页同步之后，详情、编辑、删除仍然作用于用户点中的那一条记录。
- 草稿归一化规则只有一处实现，跨标签页合并与本地加载共用。

**Non-Goals:**
- 不引入同步协议、版本号或冲突解决；「两个标签页同时改同一条记录仍后写胜出」保持为已知限制。
- 不解决「训练中对方删除记录/草稿后被本标签页写回（复活）」——`storage` 事件只给最终快照，分不清「对方从来没有」与「对方删掉了」，与既有 sessions 行为同构。
- 不改数据结构、不改存储键名、不加依赖。

## Decisions

### 决策 1：训练中分支也合并对方的草稿，而不是在写盘时做并集

在 `storage` 监听的训练中分支，把对方快照里的草稿（先归一化键）并入 `db.drafts`，**除本标签页正在编辑的那份（规范键 `dayId@date`）外，一律用对方快照覆盖**。

覆盖而不是「只补本地没有的」：对方快照就是当前磁盘上的状态。若本地留着更旧的一版（例如先收到过对方刚创建、还没填内容的草稿），下一次整量写盘会把这份旧版本写回磁盘，把对方后来填进去的重量与勾选覆盖掉——实测会让对方的草稿被判成空草稿而删除。口径与空闲分支的整量替换保持一致。

- 备选 A：写盘前把磁盘草稿与内存草稿做并集。否决——「放弃草稿」是删除操作，并集会把刚删掉的草稿加回来，除非引入墓碑标记，复杂度陡增。
- 备选 B：训练中禁止一切落盘（输入只写内存，退出时才写）。否决——落盘时机多（切后台、`pagehide`、防抖窗口），且写盘失败时的回滚路径全部要重做；与归档变更 `2026-10-20-fix-multitab-overwrite-and-rir-type` 里的否决理由相同。
- 备选 C：引入带版本号的同步协议。否决——超出本次范围，架构变化远大于问题本身。

### 决策 2：草稿归一化抽成纯函数

现有 `normalizeDrafts()`（`core.js:221-234`）直接操作 `db.drafts` 并整体替换容器，无法复用到「对方的草稿快照」上。抽成 `normalizeDraftMap(drafts) -> { out, changed }`：输入一个草稿容器，输出归一化后的容器与是否发生变化的标记，调用方决定是否替换自己的容器。`normalizeDrafts()` 改为调用它。

### 决策 3：记录定位采用「引用优先 + 签名回退」两级解析

1. 先按对象引用在 `db.sessions` 里找（`indexOf`）：命中即用。这条保持 AGENTS.md 的硬约束——重复 `id` 时也只影响用户点中的那一条。
2. 引用失效（跨标签页整量替换）时，按记录签名找回：`id` + `date` + `dayId` + 动作数 + 总组数。候选中签名唯一的用它；候选多于一个且签名仍无法区分的，判定为「无法确定」，不猜、不操作，保持现有的「这条记录已经不在了」提示。

- 备选 A：只按 `id` 找回。否决——重复 `id` 时会命中错误的记录，正是 AGENTS.md 点名要防的情况。
- 备选 B：引用失效时按内容全等比对。否决——浮点重量与 JSON 序列化顺序会让全等不可靠。
- 备选 C：跨标签页同步时不整量替换 `db.sessions`，改成按 `id` 原地更新。否决——要重新实现「删除传播」，比定位修复大得多。

### 决策 4：编辑态复用同一套解析

`state.wo.editingRef` 仍存对象引用（保持现状），但 `finishWorkout()` 保存时用同一解析函数重新定位；定位失败保持现有提示。解析结果与 `showSessionSheet()` 的删除路径共用。

## Risks / Trade-offs

- **对方删除草稿后本标签页仍持有 → 下次落盘复活** → 接受：`storage` 事件只有最终快照，无法区分「对方从来没有」与「对方删掉了」。与既有 sessions 的删除复活同构，已知限制；缓解只能靠引入同步协议，超出范围。
- **签名回退可能选错记录** → 缓解：签名必须唯一命中才执行操作，否则拒绝并提示，不猜。
- **合并草稿时同一 key 双方都有** → 保留本标签页正在编辑的那份（对方版本丢弃），与 sessions 的后写胜出一致。
- **训练中分支新增合并逻辑** → 缓解：合并只按规范键增补，不删除、不改写已有草稿内容，回归风险低。
