# Design

## Context

三处修复彼此独立，但都落在「边界状态下系统还该不该可用」这条线上：进度页的空态、Service Worker 的激活、旧草稿的恢复。相关行为契约见 `specs/` 下的 delta，动机见 `proposal.md`。

现状约束：

- 进度页的渲染入口 `renderProgress` 在可用记录为空时提前返回，导入/导出按钮、坏数据提示卡都在返回点之后。
- `sw.js` 的 `activate` 用 `caches.keys()` 全量枚举，再用「不等于当前缓存名」作为删除条件；Cache Storage 的作用域是 origin。
- `openWorkout` 已有两条时钟恢复路径：正常草稿按 `lastResumedAt` 合并中断间隔并设 2 小时上限；缺 `elapsedMs` 的草稿按 `Date.now() - startedAt` 推算，无上限。

## Goals / Non-Goals

**Goals:**

- 空态下恢复备份的路径不断开，且用户能区分「没有数据」与「有数据但不可用」。
- 缓存清理的作用域从 origin 收敛到本应用。
- 缺少已累计时长的旧草稿不再产生量级错误的训练时长。

**Non-Goals:**

- 不改变记录的存储结构、导入校验规则或统计口径。
- 不为空态新增导出入口（空库没有可导出内容）。
- 不把 `sw.js` 改成版本化资源策略，网络优先 + 预缓存清单维持现状。

## Decisions

**空态复用同一个导入按钮，而不是新增第二条导入路径。** `renderProgress` 的空态改为渲染「导入备份」按钮并调用既有的 `importData()`；导入成功后沿用导入流程自身的重渲染。备选方案是给空态单独的导入实现，会与 `validateDB` + 覆盖确认的既有流程重复，弃用。

**空态文案按原因分叉，而不是统一加一句兜底说明。** 判断依据是 `db.sessions.length` 与过滤后数量的差值：差值为 0 说明确实没有记录；大于 0 说明有记录被过滤，复用 `brokenCard` 的措辞。这样「时钟错乱导致全部记录日期在未来」的场景也有了解释，而不必为它单独造一套提示。

**旧草稿缺 `elapsedMs` 时从 0 起算，而不是并入上限 2 小时。** 2 小时上限解决的是「已知中断起点」的场景，此时 `lastResumedAt` 是可信的；缺 `elapsedMs` 的草稿没有任何可信的累计依据，按上限推算等于凭空写入 2 小时，会继续污染统计。从 0 起算的代价是丢失未知的历史时长，但这部分本来就无从得知。

**缓存清理用前缀匹配 `gym4-`，而不是维护一份白名单。** 前缀与本应用已有的缓存命名一致，新增版本无需同步改动清理逻辑；白名单在版本递增时容易漏改，弃用。

## Risks / Trade-offs

- [前缀匹配假设缓存命名始终以 `gym4-` 开头] → 后续改动缓存名时须保持前缀；该约束写入 `offline-cache` 规格，改名会是一条显式的规格变更。
- [空态新增导入按钮带来一次额外点击的风险，用户可能误触覆盖] → 沿用导入流程既有的「导入会覆盖当前所有记录（N 条），确定？」确认框；空库时 N 为 0，文案不误导。
- [旧草稿从 0 起算会低估那次训练的时长] → 只在缺少累计字段时发生，且该草稿通常来自升级前的旧版本；相比数千分钟的错值，低估是更安全的方向。

## Migration Plan

- 无需数据迁移：本地数据结构不变，旧草稿在下一次恢复时按新口径处理。
- 回滚方式为回退对应提交；缓存清理范围与空态渲染都不产生持久副作用。
