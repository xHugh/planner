# Design

## Context

本地数据只有一份 `localStorage` 键 `gym4.db.v1`，没有后端、没有版本号、没有冲突解决机制。多个标签页各自持有一份内存镜像（`js/core.js` 的 `db` 单例），写盘是整量 `JSON.stringify(db)`——这是"最后写入胜出"模型。现有 `app.js` 的 `storage` 监听只在空闲时整体替换内存数据，训练中只弹 toast 不合并。

RIR 的读取路径有三处：`getDraft()` 的旧草稿迁移、`openWorkout()` 的编辑模式（`s.rir ?? 2`）、`finishWorkout()` 的写入。`chips()`（`js/core.js`）用 `===` 比较当前值，所以字符串会让所有档位落空。`pain` 已有 `snapPain()` 做 `+v` 归一，`rir` 缺同一层保护。

## Goals / Non-Goals

**Goals:**
- 训练中收到别的标签页写入时，本标签页随后的写盘不丢对方的记录。
- 训练级 RIR 无论来自旧草稿、手改数据还是编辑入口，加载后都是数字。
- 不引入同步协议、不加时间戳版本号、不改数据结构。

**Non-Goals:**
- 不做双向冲突合并（同一份训练被两个标签页同时改的场景：仍然后写入胜出）。
- 不解决"训练中另一标签页删除记录 → 本标签页下次写盘把它带回来"（复活而非丢失，见 Risks）。
- 不改 `validateDB()`——它已经拒绝非数字 `rir`，本次是让产出始终合法。
- 不处理主题（`gym4.theme`）跨标签页同步——显示偏好，非数据。

## Decisions

**决策 1：训练中按"合并新增记录"而不是"整体替换"**
`app.js` 的 `storage` 监听在 `state.wo` 非空时改为：用 `loadDB()` 拿到新数据，把新数据里**当前内存没有的训练记录**追加进 `db.sessions`，草稿容器保持本标签页自己的不动。空闲时保持原来的整体替换 + `normalizeDrafts()` + 重绘，因为删除也要能正常传播。

去重按记录的 `id`，不按对象引用：`loadDB()` 每次都做一次 `JSON.parse`，产生的全是新对象，引用比较（`Array.prototype.includes`）对"内存里已有的记录"也永远返回 false——实测会把已有记录再 push 一遍，同 id 记录当场翻倍（既有回归用例「两个标签页相互同步」因此失败：记录数 1 变 2）。按 `id` 去重的代价是手改数据造成重复 `id` 时可能漏合并一条，这优于重复插入。

- 备选方案 A：训练中禁止一切 `saveDB()`（把输入改成纯内存，退出时才写）。否决：训练中需要落盘的时机很多（切后台、`pagehide`、防抖窗口），逐个改成"只写草稿不写 sessions"会把 `saveDB()` 的职责拆碎，且 `localStorage` 写失败时的回滚路径全部要重做。
- 备选方案 B：给每条记录加 `updatedAt`，写盘前合并。否决：需要一次数据结构迁移，旧记录没有该字段；而本场景只需要"不丢新增"，不需要"解决同一条记录的冲突"。
- 备选方案 C：训练中改用 `storage` 事件锁（写盘前再读一次）。否决：`localStorage` 没有原子操作，读-改-写之间仍可能被另一个标签页插入，收益不稳定。

**决策 2：RIR 归一放在 `getDraft()` 出口，与 `snapPain()` 对称**
在 `js/log.js` 加一个 `snapInt(v, fallback)` 小工具（`Number.isFinite(+v)` 判断，失败返回 `fallback`），在 `getDraft()` 返回前对 `dr.rir` 调用，默认值 2。`openWorkout()` 的编辑模式也走同一个入口（编辑草稿由 `s.rir ?? 2` 构造，同样可能拿到字符串——虽然 `validateDB()` 挡得住导入路径，但内存里的草稿不经过它）。

- 备选方案 A：在 `chips()` 里做宽松比较（`o.v == current`）。否决：只修显示，`finishWorkout()` 仍把字符串写进记录和备份，问题照旧。
- 备选方案 B：在 `finishWorkout()` 写入时归一。否决：训练页仍然无一档选中，用户在编辑时看不到当前值，且与 `pain` 的处理位置不一致。

## Risks / Trade-offs

- **训练中另一标签页删除记录 → 该记录被复活** → 合并策略只追加不删除，所以本标签页内存里仍持有被删记录，下次写盘会把它带回来。缓解：删除后另一标签页会再写一次盘并触发本标签页的 `storage` 事件，最终收敛到删除态；真正需要严格一致要引入同步协议，超出本次范围（proposal 已声明 Non-Goal）。
- **合并按 `id` 去重，跨标签页同一记录是两个对象** → 若两边都新写了"同一次训练"（不同标签页同时完成同一份草稿），会出现两条记录而非覆盖。这优于静默丢失，且重复完成已有 `finishWorkout()` 删草稿的防护，正常流程不会走到。手改数据造成重复 `id` 时可能漏合并一条，同样优于重复插入。
- **`storage` 事件在个别浏览器可能不触发**（已知的 Safari 私有模式等边缘）→ 行为退化为现状（覆盖），不会比修复前更糟。
- **RIR 归一会改变手改数据的显示** → 原本无一档选中变为选中默认档，这是修复的预期效果，spec 已声明。

## Migration Plan

纯代码修复，无数据结构变化，无需迁移。旧数据里已有的字符串 `rir` 在下次打开草稿时自动归一。回滚 = 还原这两个文件。
